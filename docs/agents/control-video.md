# 深度捕捉（control video）易错点全集

**实现真源** `kinema/control/` · `cli` 的 `control` 动词组与 `_ref_video` · `studio_app/app/control.js`

一句话：把一段实拍片处理成「人物深度浮雕 + OpenPose 骨骼」的控制视频，绑到镜上作
Seedance `reference_video` 发出——**运动来自源片，外观来自分镜图**。它是 previz、
简笔分镜之外的第三条运动预演路径，三者每镜互斥。

工法（源片准入、切段、对位纪律）在 `kinema-depth` skill，本文只写引擎侧的判例。

## 1. 能力归属

### ① 能力普及，不按 skill 门控

引擎里今天**零处**按 skill 分支功能。深度捕捉的闸只有三层：

    本镜绑了控制视频且仲裁判给它（`control.control_shot`）
      × `motion == native`
      × `prov.supports_reference_video`

**没有章级开关**（previz 那路的 `previz_v2v` 在这里没有对应物）：绑定就是发送的
表态，解绑就是撤回。绑定本身已经是一串不可能误触的显式动作（上传、处理、选镜、
框区间、看对照），再要一个开关是让同一个人对同一件事表两次态；一个能忘记打开的
开关就是一条静默失败路径——绑定成功、片段却一帧不发。成本关口在 `--dry-run` 与
事前额度闸，不在开关上。previz 那路有开关，是因为它有非 V2V 用法（只当末帧与
运镜预设）；控制视频段落只有 `reference_video` 一个去处，无从选择。

Studio 侧只认服务端下发的 `uses_video`——与 3D 导演台、简笔分镜同判据、同一条
`.pvz-fold` 折叠条。「不许按 skill / 画风推」是 `studio-frontend.md` §9.0 的既定纪律，
且已有可执行守卫（`test_previz_desks_are_gated_by_uses_video_not_by_project_type`
把那个函数体切出来，禁止其中出现 `d.skill` / `d.profile`）。

### ② `kinema-depth` 是能力包，不进 `project.skill`

它 `kind: capability`、`profiles: []`、`activation` 不含 `project-bound`，与画风 skill
并肩调用。route 形态在这里是自伤：编译器要求 route 声明的 profile 集合与
`config/models.yaml` **恒等**，铸一个新画风档就等于给每张分镜图无条件拼上一段
`style_prefix`，而本功能的论点恰恰是外观由分镜图决定。

`skills.validate_skill(..., bind=True)` 是执法点，判据取 manifest 的 `activation`——
声明与执法同源，不另建「哪些 skill 能绑」的第二张表。

## 2. 契约

### ③ `shots[].control` 是扁平路径串

只存裁好那一段的路径；素材 id、起点、段长、贴合方式与漂移基线全在 `shots[].gen.control`。

**嵌套字典会炸引用摘要**：`agent_gateway._document_reference_digests` 递归收集
列出键下的每一个字符串，`control` 一旦是对象，素材 id、`fit` 与 `at` 时间戳都会被
当成参考物摘要，`agent explain --stage video` 从此对每个绑定镜永远报
`references_changed`。它明确跳过 `gen`，故元数据放那里是隐形的。

### ④ 素材库不进契约

`assets/<id>/` 是一次上传的自足目录，存在性由磁盘推导（同 previz 的 reel 清单）。
因此 `control build` **全程不 load/save 章节文档**——这是多条素材并行处理不会与
绑定、编排保存互相丢更新的全部理由。

反过来：`bind`/`unbind`/`delete` 要写文档，必须持章节操作锁（CLI `@_op_locked`、
Studio `_exclusive`）。`shots[].control` 不在 `_SHOT_HUMAN_KEYS` 里也永远不会在
（它是引擎写的），所以 `Project.save()` 的三方合并对它零保护：一个持有旧副本的
gen-video 任务收尾时会把绑定悄悄抹掉，那一镜照原价发出去、不带参考视频、不报错。

### ⑤ 绝不写进 `shots[].clip`

compose 视 `clip` 为最终成片素材直接播放。控制视频是黑底灰度浮雕——写进去就是把它
当成片交付了。同 previz、简笔板的既有铁律。

## 3. 仲裁

### ⑥ 三路仲裁只在 `active_guide` 定一次

`GUIDES = ("previz", "control", "sketch")`，缺省 previz > control > sketch。
`previz.v2v_shot` 的判据随之从「没判给简笔板」改成「仲裁判给我」——否则一个显式
`guide: control` 的镜会同时满足两条 V2V 判据，逐镜任务型态不再唯一。

**control 必须压过 beats**。引擎的 `motion_plan` lint 会催作者写 `sketch.beats`，
若 beats 反压控制视频，`v2v_shot` 式的一票否决会让它一声不响不发——整章白买。
同一条改动里 `_lint_motion_plan` 对绑定镜豁免，两半缺一不可。

### ⑦ `framechain.island` 必须消费 control 判据

链态是要**落盘**的（`sync_seams` 写 `transition.auto="island"`）。孤岛判定看不见
control 就会出现：链图按衔接焊缝、实发却是 V2V 分支（那条分支根本没有首/末帧槽）。
两个开关分开传而不是并成一个——它们真的可以一开一关，并起来会让关着那一路的镜
也被判成孤岛。

## 4. 成本与请求

### ⑧ 参考视频的投影只有一份

`cli._ref_video(s, previz_on=, control_on=)` 是报价、dry-run 清单、逐镜行文案与
请求体四处的唯一来源。`_plan_cost` 与 dry-run 循环本就各自抄了一遍加价逻辑——只教会其中一份，
事前闸预留的额度就少于真实账单，而整套测试照常全绿。

### ⑨ 控制视频的 V2V 进人脸阶梯，previz 不进

官方的互斥规则拦的是 **first/last frame 与参考媒体混发**，不是「参考图与参考视频
不能同发」——参考图 0~9 张、参考视频 0~3 段、参考音频 0~3 段可以自由组合，总文件
数 ≤12（火山方舟 Seedance 2.0 文档）。V2V 分支的图本来就挂 `role=reference_image`，
再挂几张同 role 的参考图与那条规则不沾边。

把 V2V 一并归进「首帧/衔接」那一类恒判路线 A，后果是写实档的复刻镜**发不出去**：
分镜图挂着设定图生成、属图生图，人脸受信豁免天然不成立，路线 A 必被建任务时拒，
而能把受信身份图送进请求的只有降级路线。判据因此拆成两支：控制视频进阶梯
（`_control_v2v`），previz 那支照旧恒 A——它的参考视频是无材质灰模，与取景地契约对撞。

两条随之而来的纪律：

- **V2V 恒不走 B**：板与控制视频是两个并列的运动权威，盘上恰好有板也不挂。而
  无板在这条路上不是缺口——控制视频逐帧给定走位与景别，比板还硬，路线理由要照实说，
  照搬「构图交提示词兜底」会把降级里最强的一档报成最弱的。
- **互斥判在仲裁层不在 provider 层**：provider 看到的全是 `ref_images`，分不出
  哪张是板、哪张是身份图。

### ⑩ 段长恒 4~15 秒，与别名的 `max_duration` 无关

三个数字来自三处，别混：4~15 是输出时长档位（`previz.snap_duration`，与 provider 的
`billable_seconds` 逐值对拍）；2~15 是 `input_video_seconds` 钳**计费数字**的区间，
它不裁文件；30 是 `seedance-2.5` 放宽的**输出**上限，参考视频仍只收 15。

`bind` 在镜长超出时直接拒绝并要求拆镜。静默截断是拿 15 秒的运动去演 20 秒的镜。

### ⑪ 裁段必须贴合章节画布

`ratio_mode: adaptive` 的别名遇到参考视频会发 `ratio="adaptive"`，成片就跟着参考视频
的几何走而不是画布。所以 `bind` 的裁段带 `pad`/`crop` 贴合，且**重编码不 `-c copy`**
（按关键帧取整会让起点漂到最近的 I 帧，而选段的意义正是起点精确）。

多比例章节按主比例裁一次，与 previz 现状一致。

### ⑫ 参考视频必须是公网 URL——但判据是「能力」不是「默认档」

同 previz ⑤：视频参考不接受 base64/data-url/本地路径，CLI 层经 `MediaStore.upload`
预解析。`--mock` 下跳过上云直接给本地路径。这一抛发生在计划循环内、任何生成之前，
不会造成部分花费。

**闸判 `MediaStore.configured` 而不是 `enabled`**：前者是「provider + 桶 + 位置 +
密钥齐备」，后者是「上云是整份工作区的默认档」。为一条视频链接把所有分镜图、
设定图都搬上云是冗余的——`media.backend` 保持 `local`，只有参考视频与口型精修
这两条「协议层只收公网 URL」的路按需上传，文档里存的仍是本地路径。
`oss sync` 那类整体迁移仍判 `enabled`。

### ⑬ 区间说了算，`dur` 跟着走

`bind` 收 `start` + `end`：段长 = `round(end-start)`，随后**写回该镜 `dur`**。
两个数字各说各的就是运动被拉伸或截断——控制段与成片 1:1 是本特性的地基。
落在 4~15 之外**直接拒绝而不是钳进去**：静默钳位就是拿 15 秒的运动去演 20 秒的镜，
账单照收。省略 `end` 时沿用旧口径（段长由 `request_seconds` 定，`dur` 不动）。

写 `dur` 之后要**再问一次 `request_seconds`**：dubbed 的配音比 dur 长时窗口会被顶回去，
那是真冲突（这一段的运动与台词长度对不上），只能报错让人改台词或改区间。

### ⑭ 重传同一个源片得**新素材**，绝不覆盖

素材 id 是 `<文件名 slug>-<内容指纹前 4 位>`：指纹而不是文件名，两个都叫
`export.mp4` 的不同源片因此不会撞进同一个 id。但**同一个文件重传会撞上自己**，
而就地覆盖是不可逆的——旧产物被顶掉，已绑的镜却还指着照旧产物裁出来的段落，
盘上那一段与素材从此对不上，全程没有任何提示。

而重传同一个文件恰恰是常规操作（上一次处理得不理想想重来、想留两份各切各的段）。
故 `build_asset` 的 id 回退走 `unique_asset_id`：撞了就缀 `-2`、`-3`。要就地重建
走显式 `--asset <既有 id>`，那是明确表态不是手滑。

### ⑮ 一镜只收一条控制视频，换素材必须先解绑

同一条素材重绑是**改区间**（回来重框，最常做的事），照旧放行；换成另一条素材是
**换运动源**，`bind` 直接拒。两者代价不同：换素材时这一镜的段落文件被就地重写，而
「它演的是哪条素材」只在 `gen.control.asset` 里换了个 id——回头没人能从成片上看出
运动源是什么时候变的。解绑本就是一步操作，做成显式的一步比事后翻 sidecar 便宜。

两个弹层各按自己的判据压暗不可选的行（`blocked` 由调用方给）：处理弹层里已绑的镜一律
不作候选（那条绑定要等几分钟才落下，到时才顶掉旧的运动源，人早已不在这个页面上）；
绑定弹层里只压绑着**别的**素材的镜，绑着当前这条的仍可选——那就是回来改区间。压暗时
**「解绑」按钮保持全亮**：那颗按钮正是这一行的出口，连它一起压暗就成了死路。

**与 previz 的互斥在登记时两头都拦**：有 previz 的镜要绑控制视频须显式 `--replace-previz`
（绑定弹层的摘要行与 toast 把「将摘除 3D 预演」明说出来）；反过来绑着控制视频的镜
不接受 previz 登记（`register_previz` 直接拒，CLI 与 3D 导演台的渲染同一条路径）。
两条参考视频争的是同一个槽，靠缺省仲裁悄悄压掉另一路的话，用户框过区间的那条绑定
一声不响就不发了。

**片段的 `done` 锁不拦绑定与摘除**：绑定/摘除运动源是人对这一镜的直接决定，与版本
回滚、宫格换选同类——决定本身就是审阅结论，片段随之作废置 retake
（`review.retake_by_decision`，锁不豁免）。锁挡的是引擎自行重生（`--force`、血缘扫描、
批量改词、Agent 计划）。三路的绑/摘/表态都走这一条：`bind_shot` / `unbind_shot`、
`register_previz` / `clear_previz`、`sketchboard.set_guide` / `clear_board`。绑与摘必须
同一条规则：若摘除放行而绑定被锁拒，文档说没绑、锁定的片段却是按控制视频生成的，
而唯一能回到一致的动作又被同一把锁拒绝。

镜态闸（转场 / omt / 有 previz 未 `--replace-previz` / 绑着别的素材 / 镜长超出
4~15）收在 `bind_preflight`，`control build --bind-shot` 在处理源片**之前**过它，
Studio 上传时点了镜也在派任务之前过：这几条都不依赖素材内容，跑完几分钟才发现
镜不能绑，等于让人白等一趟再重传，而失败只留在任务日志里。预检按随后要绑的那条
素材判：`--asset <既有 id>` 就地重建时，绑着同一条素材的镜是「重建后重绑」、照常
放行；没点名素材则 id 待派，任何既有绑定都算绑着别的。镜长带宽只在整镜自动绑时
查——框区间的绑定由区间定段长。`guide` 表态入口对三路一视同仁：`sketch use --guide control`、
Studio `/api/sketch/guide` 与分镜卡的仲裁徽章合法值都取 `sketchboard.GUIDES`。徽章按
引擎下发的 `guide_lanes` / `guide_active` 渲染，配置了两路及以上时出现，显式指向空槽时
单路也出现并标红；点击弹选择层列出已配置的路径，另有「自动仲裁」清掉显式表态。
`control_binding` lint 判的是「绑了控制视频但 `active_guide` 不是它」，previz 共存与显式
guide 指向别处都在这一条里。

### ⑯ 对照片绝不进请求也绝不进成片

三份东西三个去处，别混：

    control.mp4 裁出的段  → shots[].control  → 发给 Seedance
    shots[].clip          → compose          → 烧进放映
    compare.mp4 / shot_N_compare{2,3}.mp4  → 只经 Studio 预览字段下发

横排画面进了前两条中的任何一条，出来的就是一张分屏成片。

绑定改了区间就把两档 `shot_N_compare*.mp4` 与它们共用的源片段删掉（`_drop_compare`）——
对照片是照旧区间拼的，留着就是在说另一段的事。

镜级两档（出片前二合一、出片后三合一）**各占一个文件名**：合用一个名字的话，成片
落下之后盘上那份二合一就成了会被当成三合一播的陈货，而它本身并没有过期。

### ⑰ 段落带源片音轨，发出去的是它的无声副本

`shots[].control` 带源片同区间的音轨：审看恰恰要听——这一段起没起在拍点上、骨骼
跟没跟上节奏，光看黑底浮雕判不出来，Studio 的 `@视频1` 点开的就是这一份完整的复刻
内容。而本章是 native，声音由模型生成，把实拍源片的背景音一并发过去等于拿账单赌模型
不拿它做文章，所以 `cut_segment` 同时出一份只保留视频流的副本 `shot_<id>_control_mute.mp4`
（stream copy，不重编码），`send_path` 把它投影成上传的那一份；血缘与 `gen.control`
记的仍是段落本身。段落没有音轨（源片无声）就没有副本，原样发；换绑到无声素材时上一条
素材的副本随段落一起清掉——发送按副本优先，留着它发出去的就是另一段运动。

分镜卡的「◆ 深度」仍开对照片而不是直接播 `s.control`：源片与深度并排、出片后再加
成片，才看得出骨骼有没有跟住动作。出片前是二合一（左源片段 | 右控制段）。

**对照片的音轨恒取源片那一路**（`audio_from=0`），三个规格同一条规则：控制段带的本就是
同一段源片音轨，成片段则常常本来就没有声音——取成片那一路的结果是三合一照样静音。要听
模型出的声音，播分镜卡上的成片段本身。放映窗不挂通往媒体地址的外链：那是整页跳转，
点了就离开工作台去看浏览器的裸播放器。

**成片要那段音乐，走章级 `control_bgm: true`，不走参考视频。** 模型的原生音是生成的，
不会原样复现参考音频，把音乐塞进参考只是给它加戏的机会；而控制段与成片 1:1，绑定区间
在源片里对应的那段音轨落在该镜在时间轴上的位置，就与舞步逐拍对上，本地 ffmpeg 零成本。
实现在 `control/soundtrack.py`：按 `Project.timeline` 逐镜顺排，绑定镜取源片段、其余镜
填等长静音，`concat` 成一条与片长等长的音轨，再做 BGM 入轨的响度归一（`bgm_gain_db` +
`master_filter`），写成章节的 BGM 文件（`audio/bgm.*`）——之后母线电平与末级归一都是曲库
BGM 的同一条链（`compose.use_bgm_for` 把它与 `native_bgm` 视作同一条母线的两种来源，
同样与配音混烧互斥）。幂等判据是段落表指纹（`soundtrack_signature`）而不是片长：重框
区间、换素材都不改片长，却已经是另一段音乐。未绑定的镜留静音。

**这条音轨是这一章的主音乐，不是配在人声下面的背景乐**（`compose.bgm_is_program`）：
native 章的主轨是片段原生音，缺省配乐链会按「有人声在场」处理 BGM——压到 0.3、挖掉
2 kHz、再由环境声触发 sidechain 闪避，末级量到 -28 LUFS 后推 +12 dB，限幅器整段在
削峰。舞曲的主角是舞曲，所以 `control_bgm` 下母线取独奏电平，不让路、不闪避。

原生音本身还得退一档（`NATIVE_BED_GAIN`，与混烧时原生音作床同一电平）：它的积分响度
只有 -30 LUFS，脚步与衣料的瞬态却顶到 -1 dBTP，按 0 dB 入混、末级再推 4 dB 之后限幅器
逐个瞬态在压，音乐随每一下脚步一起被按下去——积分响度上音乐高出 9 dB，听感却是被原声
盖住。退档后瞬态落在限幅线之下，音乐才真正在前面。

**成片相对控制段的整体偏移由引擎量，配乐随之平移**（`control/sync.py`）。我们这一侧的
时间链是确定的——裁段、请求秒数、配乐区间三者 1:1——量不到的只有模型那一段：它跟随参考
视频的走位与节奏，但不保证逐帧对齐。`music` 阶段把两路画面按同一帧率取帧间差分能量做
互相关（`estimate_lag`），偏移记进 `gen.control.sync`；相关峰不低于 `SYNC_MIN_CORR` 且
落在 `SYNC_MAX_LAG_SEC` 窗口内的才够格，够格的平移该镜配乐在源片里的起点
（`soundtrack.cut_start`），偏移进段落表指纹。只量一个整体偏移：模型在镜内忽快忽慢那
部分，平移救不了，只能重生成，所以相关不够时不动配乐——宁可差几帧，也不把音乐挪到一个
错的位置上。`control compare` 只报不记（它不持章节锁），记录归 `music`。实测
seedance-mini 复刻 12 秒舞段：整体偏移 0 帧、相关 0.59——模型对整体节奏跟得住，镜内
动作幅度与源片不是逐帧同形。

### ⑱ 拼接：先归一帧率，再按长边定方向

`hstack`/`vstack` 遇到各路帧率不一致时按最快那一路补帧：出来的对照片**时长对而
帧数翻倍**，逐帧比对当场失真。三合一的三路本就来自三处（源片、控制段、厂商成片），
厂商给的成片帧率不保证跟章节一致。故 `stack_args` 每一路都先过 `fps=`，基准取
控制段——那是真发给模型的那一份。

**摞的方向按画幅长边定**：竖画幅横着排、横画幅竖着摞。16:9 的两格并排是 32:9、
三格是 16:3，而灯箱的播放位定宽（`.cin-player video { width:100% }`，高度受 82vh
封顶）——画幅越扁，它能给出的高度越少，每格反而比换个方向摞时小一半。归一的那一维
随方向换边：`hstack` 要各路同高、`vstack` 要各路同宽，跟错了 ffmpeg 直接拒。

**成片与素材画幅取向相反时另起一行或一列**（`stack_args` 的 `tail`）：竖拍素材配 16:9
成片是常态，把横的成片塞进竖格里只剩中间一条细画面。故取向相反的那一路不进主拼接——
竖片横排时落到下一行、宽对齐整行；横片竖摞时贴到右侧、高对齐整列；它单独占一行或
一列，只等比缩放不裁不补。判据在 `build_shot_compare` 用 `probe_dims` 取成片宽高（只读流信息，
不数帧），同向仍照旧并入主拼接。

各路的裁切（`-ss`/`-t`）也在 `stack_args` 里一并做：起点本就各不相同（源片与控制
视频从绑定区间起裁、成片本身就是那一段），先落中间文件再拼等于每格编码两次。

二合一在**帧数核对之后**才拼：先确认控制视频与源片帧数守恒，再拼；顺序反了会把一条
已经错位的控制视频拼成看着挺像的对照片。

### ⑲ 对照片每格取**素材原片**的画幅，不是章节画布

发出去的那段控制视频必须按画布贴合（见 ⑩，那是承重的），但它只是投递格式：一段
9:16 的实拍装进 16:9 画布后，`cropdetect` 量出来只有 608/1920 是画面，68% 是补出来
的黑边。把这层补边一并摞进对照片，看到的就是几格黑底中间几条细人影——而方向判据
若也跟着画布走，竖片还会被判成横画幅竖着摞，两头不落好。

所以镜级对照片的前两格直接取 `assets/<id>/` 里的 `source.mp4` 与 `control.mp4`
（未贴合的原片，pad 贴合下内容与发出去那一段逐帧相同），成片那一路按章节画布出、
与素材画幅不一致时 pad 进同一格。各格等大是硬要求：不等大时，看到的第一件事会是
「几格不一样大」而不是运动对不对。守卫按「两格与三格的格宽必须相同」判——只查合成
宽能不能被 3 整除是查不出来的，398+404+404 照样整除。

`--fit crop` 是例外：发出去的段只保留画布比例的中央区域，原片全幅里有模型没收到的
画面。故前两格按裁好那段的画幅套同一条裁切（`gen.control.fit` 决定，滤镜与裁段共用
`io.fit_filter`），画幅随之取章节画布、方向照长边判。

帧率仍以发出去的那一份为准（成片理应贴着它走，帧数也据此守恒）。`shots[].control`
本身一个字节不动。

### ⑳ 桶名不进 `storage.yaml`

那份文件随仓库分发，填进去的桶名会跟着提交。`bucket`/`region`/`endpoint`/`public_base`
与 AK/SK 走同一条链（env > secrets.local.json > secrets.yaml > storage.yaml），
两份 secrets 都在 gitignore 内。守卫钉住模板里的 `bucket`/`region` 恒为空串。

## 5. 感知层

### ㉑ rtmlib 不进 extra

它的 METADATA 同时声明 `opencv-python` 与 `opencv-contrib-python`，两者装进同一个
`cv2` 命名空间、后者会被前者覆盖，而 PEP 621 的 extra 表达不了 `--no-deps`。
装完 `engine[control]` 再跑一行 `pip install --no-deps rtmlib`。

`models.readiness()` 因此兼查 `hasattr(cv2, "ximgproc")`——被覆盖的安装照常 import 成功，
只有用到引导滤波才 AttributeError，而那已是渲染中途。

### ㉒ 权重不静默下载，就绪只进 doctor

约 115 MB，跑在一条本来就要几分钟的链前面，静默拉取会把「网络卡了」表现成
「处理卡住了」。缺文件直接抛，由 `control fetch` 显式取。

**不进 `setup --check` 的 `checks`**：那一份任何一项为假就把 `ready` 打成 false，
而 AGENTS.md §1.3 把 `ready=true` 当作「直接开工」的信号——一个每台新机器都缺的
可选栈会永久卡住它。同 `vision` extras 的先例。

### ㉓ 每个长跑 ffmpeg 的 argv 上必须有 `_work/`

孤儿回收器（`ffmpeg.find_orphan_ffmpeg`）匹配 PPID==1 **且**命令行里含 `_work/`。
一个读用户桌面文件、写向 `pipe:` 的解码器不带这个标记，父进程被杀后会永远占着一颗
核心。**这就是源片必须先归一进 `assets/<id>/source.mp4` 再开跑的原因**——那不是
格式洁癖。归一同时解决可变帧率（VFR 下「一帧进一帧出」在解码端就不成立）。

### ㉔ 时序滤波的卷积必须与序列长度无关

`np.convolve(mode="same")` 返回的长度是 `max(信号, 核)`。深度窗的核是 73 帧，任何
短于 3 秒的素材都比它短，结果比输入还长、随后按输入长度的掩码索引直接越界。
写法是全卷积后取中段 `[r:r+len]`。原型正是在这里崩的，而测试用的合成片恰好落在
这个量级。

### ㉕ 遮罩：人物框内**替换**而不是并集

整帧那张分割遮罩是 256² 铺满全画幅——在 540×960 的工作分辨率上，一个遮罩像素管到
2×4 个源像素。把它与每人裁切出来的精细遮罩取并集，只会往外加面积、永远减不掉，
精细轮廓当场被吹胖成一团（实测夜景宽松衣物的源片上，人被糊成一个无定形块，
躯干里还留着洞）。做法是：**人物框内用精细结果替换，框外才留粗遮罩**——姿态没检到
的人还得靠它兜住。

### ㉖ 检测与轨迹的三个阈值都不能写死帧数

· `MIN_KPT_MEAN` 一次检测的**平均**关节置信度地板：背景里的车、反光、衣物褶皱能
  凑够 6 个刚过 `KPT_THR` 的关节，逐条都合格而整体很虚——实测一段**单人**夜景里
  凭空多出一条 1.9 秒的轨迹，在成片里就是一条乱挥的肢体。
· `MIN_TRACK_SEC` / `GAP_MAX_SEC` 按**秒**而不是按帧：8 帧在 30fps 下是 0.27 秒、
  60fps 下只有 0.13 秒，同一份阈值在两种源片上严宽差一倍。补洞窗口按秒放宽后，
  同一段素材里真人的出现率从 81/90 帧升到 90/90——运动模糊造成的连续漏检被接住了。

### ㉗ 编码**绝不能加 `-shortest`**

它看起来在防「音轨比视频长几十毫秒」，实际是把帧数守恒交给了音频的采样对齐：
AAC 一帧 1024 采样，任何时长落不到帧边界的片子（也就是大多数）音轨都会比视频短
一点点，`-shortest` 于是砍掉最后一个视频帧——实测 3.000 秒的片子出来 89/90 帧，
整条链直接判失败、几分钟 CPU 白跑。反过来音轨长一点完全无害：视频帧数由我们喂进去
的帧决定，绑定裁段与它的无声发送副本同样只以视频帧为准。

### ㉘ 进度打印不该杀掉正在跑的活

Studio 把 build 派成子进程并读它的 stdout。Studio 一重启管道就断，下一次进度
`print` 抛 `BrokenPipeError`——那会把已经跑了几分钟的处理连同半成品一起葬掉。
进度是**汇报**不是活，没人在听不是失败。同理 `clear_incoming` 的路径比较两边都要
`resolve()`：CLI 传相对路径而 `incoming_dir` 恒是绝对路径，不 resolve 就是一句
永不执行的死代码，上传件在盘上留成双份。

### ㉙ sidecar 一律原子写

`asset.json` 每 24 帧回写一次进度，而 Studio 扫描器每几秒读同一个文件。非原子写
必然被读到半截，而读端按惯例把解析失败当「没有这条素材」——表现是处理中的素材在
页面上闪烁消失。走 `storage.atomic_write_json`。

### ㉚ 单条源片 30 秒上限，章内 build 互斥

`jobs._job_timeout` 对没有 `meta.shots` 的任务硬顶 1800 秒然后 `killpg`——超时被杀时
CLI 跑不到失败处理，sidecar 会永远停在非终态。按实测每源秒约 17.5 秒算，30 秒源片
落在 525 秒左右，离那道墙有三倍余量；而真正发出去的段本来也只有 4~15 秒。

互斥落在 `control/` 目录内的 `.build.lock`（跨进程，CLI 与 Studio 共用一把）——
`jobs.spawn_seq` 没有队列，两次调用是完全并行的。

## 6. 已知限制

- 人物整体走近/走远这一维被深度归一化掉了（保留的是身体内部的前后关系）。要留住它
  需要静止背景像素做锚，而那在运镜素材上不成立。
- 两人完全重叠又同时换位时可能交换 id（贪心 IoU 的已知弱点）。
- 段内有剪辑点的源片处理出来是跳变的骨架——先剪成单镜头连续片段。
- 只在 macOS arm64 实测过；Linux/Windows 的 wheel 存在但未跑。
- 控制视频与分镜图的人物比例/站位不一致时模型会折中。**引擎不自动对位**——对位需要
  视觉理解，交指挥层（`kinema-depth` 的「对位纪律」）。
- 配乐对拍只量整体偏移。模型在镜内局部提前或滞后，在互相关上表现为相关值偏低而不是一个
  可用的偏移，配乐不动；那一镜只能重生成或改镜。

## 7. Studio 形态

章节页 DV 区块，排在 3D 导演台与简笔分镜之间（三台按「运动从哪来」由重到轻：
3D 是自己排的戏、深度是照着实拍复刻、简笔只给节奏拍表）。

**与简笔分镜台逐条同构，且共用同一段样式规则**（style.css 里 `.skb-*` 与 `.cvc-*`
并列在同一条选择器上）。两张卡是同一类东西的两个实例，各存一份样式必然慢慢长歪，
而长成两个样子会让章节页读起来像三个软件。

素材产物五件：`control.mp4`（喂模型）、`compare.mp4`（左源片右深度的二合一，
**缩略带点开放的是它**——单看深度判不出骨骼有没有跟住动作）、`styled.mp4`
（白色浮雕，只给人看，留在素材目录里；放映窗不挂通往媒体地址的外链，见 ⑰）、
`sheet.png`（**两格**对照图，读者是缩略带上 84px 高的一个格子，四格挤进那个宽度后
每格都太小）、`strip.png`（每半秒一格，选段窗在它上面拖）。镜级另有按需生成的
`shot_N_compare2.mp4` / `shot_N_compare3.mp4`。

**不另起全幅路由**：卡上一条缩略带看产物（点开是视频灯箱），主按钮开弹层。

「◆ 开启深度捕捉」是拖放上传 + **可选**单选一个镜：处理要跑几分钟，跑完人多半已经
离开页面，让他回来再点一次绑定是白等一趟。选了就随 `--bind-shot` 一路带到 CLI，
处理成功后就地绑（`build` 本身刻意不持章节锁，绑定那一步单独取一次）。

「◇ 绑定分镜」是**选素材 + 单选一镜 + 框区间**：顶上一条素材封面带，中间分镜行，
下面缩略条上拖双把手、上方同步播二合一。单选而不是多选，是因为区间现在逐镜可调——
多选就只能给所有镜一套区间，那等于把「自己框哪一段」这件事又收了回去。已绑的行上
就地解绑。摘要行必须把 `dur` 的变化明说出来（`镜 3 时长 12.0s → 7s`）：框区间改的
不只是「用素材的哪一段」。

素材带印**封面**而不只是文件名：一批素材常常都叫 `IMG_0421.mp4`，只印名字等于让人
凭记忆选；封面用处理时留下的 `sheet.png`（左源片右深度），一眼认得出是哪条表演。
弹层开局就落在最靠前的未绑定镜上——进这个弹层就是来绑一镜的；换素材时若原选中的镜
正绑着刚被换掉的那条（在新素材下不可选），选中位往下落到最靠前的未绑定镜，没有空镜
就清空舞台等人先解绑。

选段条上**三种手势各管一件事，互不串台**——拖把手只动这一端（另一端钉住，这才是
修剪）、拖选区本体整体平移、在条上按一下只移播放头。左把手若做成「整体平移」，
用户想缩短开头却发现结尾跟着跑，一次也对不准。选区内的「按一下」与「拖」按 3px
位移分辨，两种意图不必抢同一次点击。

段长恒取整秒（引擎按 `round(终点-起点)` 定段），取整时**只动正在拖的那一端**；
顶到素材首尾时另一端才让步，否则就够不着片头片尾。把手贴选区**内侧**而不是骑在
边线上：条为了压暗选区外要 `overflow:hidden`，骑出去的那一半会在两端被整齐切掉，
而那正是最常拖的两个位置。

**分镜行是 `div` 不是 `label`**。label 的激活行为会把点击转发给内部第一个可标注
控件，而「解绑」是 `button`（正是可标注元素）——行做成 label 时，点行内任何一处
文字都会静默解绑，用户以为自己只是选中了这一行。这条路不走冒泡，`stopPropagation`
拦不住。守卫在 `test_frontend_integrity` 里按源级判：label 该包 checkbox 与 input，
包了 button 就是选错了元素。

素材格左上角标出绑给了哪几镜（`SHOT 01 +2`，与简笔板的格签同形）：一条素材可以切给
多个镜，不标的话几条摆在一起就分不出哪条已经用上、哪条还白放着。

分镜行的悬停底色**自左向右扫入**（`.cvc-row::before` 的 `scaleX`）：一列等宽扁平行
只靠变色很难看出指针停在哪一行。选中行的扫入层换成选中色本身——底色不透明，不换的话
悬停时会把选中态整个盖掉。

分镜卡的「◆ 深度」角标随产物到哪一步而变：出片前是二合一、出了成片是三合一
（第一次点开现拼几秒）。**两档都是对照片，不直接播 `s.control`**——并排才看得出骨骼
有没有跟住动作；单看那一段（带源片音轨）走提示词面板的 `@视频1`（见 ⑰）。拼好的 URL
**由接口回，前端不自己拼路径**——那份路径到媒体 URL 的映射只该有 `_murl` 一处。

选段器的预览**不静音**：框一段舞蹈要的正是「起在哪个拍点上」，静音框只能靠猜。
出声只在按下播放键之后（那里没有自动播放这条路），不会有人被突然吵到。

卡内的三条 blocker（感知栈未就绪 / provider 不支持参考视频 / 本集不是 native）措辞与
CLI 同源，页面与终端不许说两套话；未就绪时卡上直接印三行安装命令。卡上没有开关：
绑了就发（见 ①）。`/api/control/seedance`（`gen-video -m b` 的后台任务形态）只作 API
存在，页面上出片仍走分镜卡的生视频入口。

章节页的轮询签名必须并进素材进度：`control build` 从不碰章节文档、`updated_at` 不动，
只看文档签名的话整个处理期 3 秒一次的轮询都判「无变化」，进度条纹丝不动。守卫在
`test_control.TestLiveFeedback`。

CLI 侧两个不在主流程里的开关：`control build --no-styled` 跳过白色浮雕精细版（省约
三成渲染时间），`control fetch --check` 只查权重不下载。
