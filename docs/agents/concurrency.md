# 并发生成纪律

**实现真源** `kinema/parallel.py` + `cli` 三处三段式

图像/配音是逐项独立的 API 调用，串行等于把十几次网络往返排成一队——`project refs`/`gen-image`/`tts`
已并发（`--concurrency N`，缺省 4）。但并发的风险全在「错得悄无声息」，故有以下纪律。

## 1. 四条核心纪律

### 1.1 工作线程只产文件，主线程只改文档

`save`/`add_cost`/`mark`/`review`/`lineage` 一个都不许进工作线程。两个线程各改一半再各自整份写盘
就是丢更新——不报错，只是某张「生成了没登记上」。

### 1.2 一一对应按 key 不按完成顺序

并发下完成顺序天生是乱的，回调与返回值都按**提交顺序**，日志因此与串行一字不差。

### 1.3 记账排在登记之后

`add_cost` 是「先入账再抛」，抛在登记前面会把这张已生成已付费的图丢掉登记、重跑再买一次。
超限只置停派标志让本批收尾跑完——在飞的钱已经花了，结果必须收。

### 1.4 重试只认瞬时错误

`providers/_util` 已在 HTTP 层退避 429/5xx，本层只兜逃出去的连接错误。业务性 4xx（违规/余额/租约
失效）一次都不重试，否则是白付多次钱还多触发风控。产物已落盘则走幂等护栏直接当成功。

## 1.5 跨进程写回：系列文档只许锁内重读后合并

上面四条管的是**一个进程内**的线程。系列文档（`project.json`）还有一层：Studio 把生成类操作
派成 `python -m kinema …` 子进程（`studio/jobs.spawn_cli`，无队列、无准入检查），子进程与
Studio 的请求线程写同一份文档，进程内的锁对它们之间的竞争完全无效。

制度与章节文档同底座（`locking.save_lock` 的 flock），落点在 `Series.save`/`Series.commit`：

- `save()` **不合并**，只服务「刚加载就改、立刻写回」的短操作；
- 加载与写回之间隔着生成、上传或任何等待的，一律走 `commit()`——锁内重读磁盘最新副本，
  再按身份把本轮产物合并进去。块内必须**重新定位实体**，块外拿到的 dict 引用已经作废；
- 耗时的生成放在块外，锁只覆盖登记。

三条长任务按这个形态分两段提交：`cmd_gen_refs`（计划期归档 + 回填期合并）、
`refine.refine_asset`、`cmd_cover` 的系列主视觉。归档必须在**计划期**那次提交里落盘：
它已经把旧图 `shutil.move` 进了版本栈，版本条目若只留在内存，回填期的重读会把它丢掉，
下次归档按 `len(hist)+1` 重新编号就会撞上已有的归档文件名。

嵌套要留意：flock 按「打开文件描述」判归属，同一线程再开一个句柄申请同一把锁会自己等自己，
故 `commit()` 块内的那次 `save()` 走重入分支，只有最外层真去申请。

## 1.6 非表态编辑与生成任务串行

章节文档的 `Project.save` 只按表态键做三方合并，作者字段、`shots[]` 结构与合成期参数不在其中：
生成/合成任务持有的旧副本收尾写盘会把这类编辑写回旧值，而编辑方已经拿到成功。
所以这类编辑与生成任务共用同一把章节操作锁，被占即拒、不排队：Gateway `plan apply`
（`_ChapterLock` 先持操作锁再持文档写锁）、`batch edit/undo`、`transition add/rm/sync`、
`chapter set`（`_op_locked` 或锁内装载）、Studio 的全部非表态写端点（`_exclusive` 锁内装载：
转场、垫图、特效、水印、字幕样式、previz 编排与摘除、简笔板摘除）与移动画布产物的门
（宫格点选、素材直供、局部改造、previz 登记、简笔板生成、回滚），以及系列→章节的逐章传播
（`Series.chapter_write`：设定字段对齐、音色表、垫图、大纲、设定图血缘）。
生成/合成/一条龙的章节装载在锁内完成，锁外装载的副本可能已被刚收尾的另一操作改过；
`assemble` 的审阅闸与两道发问闸持只读副本，表态经 `Project.mutate` 落盘。
表态类命令（`review set`、`consistency set`、`decision add`、`lineage mark`、`verify` 结论）
不取操作锁，按磁盘现状 `Project.mutate` 写单键，长任务期间照常可用。
派子进程的端点在锁外派，子进程自己也要过这把锁。
合并白名单不为这类编辑扩大——引擎副本的纪律是「主线程只改文档、工作线程只产文件」，
不做三方合并器。操作锁的进程内重入按线程判（键含线程号与真实路径）：Studio 的请求线程各自独立。

## 2. 进度反馈是这套设计的必需品，不是装饰

既然按提交顺序消费，第一件活慢时后面早跑完的结果都排在队里不打印，观感就是「一直卡着毫无反馈」
（实测被点名）。故：

- 主线程等 head 时按 `tick`（缺省 3s）醒一次，报「已完成 n/总数 · 已用时 · 正在跑哪几件」——
  点名在途那几件，用户才知道卡在谁身上；
- 逐项结果必须在 `_apply` 里**随完成流式打印**，攒到批次结束再统一打等于十几张图跑几分钟一行不出。

### 2.1 打印器分两态

| 环境 | 行为 | 原因 |
|---|---|---|
| TTY | 原地 `\r` 刷新 | 交互终端要实时感 |
| 非 TTY（Studio 把任务 stdout 存成日志文件） | 只在数字变化时落行 | 每 3 秒刷一次 `\r` 会在日志里堆成一坨乱码 |

## 3. 真实的串行依赖必须显式排除

首镜强锚（后续镜拿首镜成品当参考图）先单独跑完再并发其余。

## 4. `gen-video` 的并发是显式 opt-in

Seedance 按 providers 别名单价按秒计费（4K 翻倍，单价以 `config/models.yaml` 为准），静默并发等于
同时下多张高价订单。因此：

- 缺省恒串行；
- **不吃 `KINEMA_CONCURRENCY` 环境变量**——给生图配的全局值不该顺手把视频也并发了；
- 显式 `gen-video --concurrency N` 才开；
- 预算闸事前对账、失败即停派、parallel 层 `retries=0` 防重复计费、4K 档强制串行；
- `run`/`--auto` 一条龙里恒串行。

## 5. 逃生舱

`--concurrency 1` 完全不起线程，与既有串行行为逐字一致，可直接对拍。
